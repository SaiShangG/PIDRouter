# CAD Simple Viewer Example

A vanilla TypeScript demo that shows how to embed [`@mlightcad/cad-simple-viewer`](https://github.com/mlightcad/cad-viewer/tree/main/packages/cad-simple-viewer) in a web page: open DXF/DWG files, drive viewer commands from a small toolbar, and lazy-load HTML/PDF export plugins.

## Features

- **Local files** — Open `.dxf` / `.dwg` via file picker (toolbar **Open** or center **Open File**)
- **Sample drawings** — Sidebar loads predefined files from the [cad-data](https://github.com/mlightcad/cad-data) CDN
- **Viewer toolbar** — Zoom fit, zoom window, background toggle, pickbox size, line-weight display, export HTML/PDF
- **Lazy plugins** — registered from `@mlightcad/cad-*-plugin/register` in `src/register.ts`; `-chtml` / `cpdf` / `csvg` load plugin chunks on demand (`chtml` runs the same command-line export when no dialog command is registered)
- **Browser-only** — Parsing and rendering run in the browser (Web Workers + WebAssembly for DWG)
- **Responsive layout** — Sidebar + viewer pane; stacks vertically on narrow screens
- **Process phases** — Create processes and phases, clone the previous or any historical phase, and navigate phase snapshots without replacing the existing viewer tools
- **Back to top** — When the process/phase list is scrolled down, use the button in the fixed process header to return to the list top without changing the active phase.
- **Process switching** — Switching processes resets the list to the top without changing the destination process's active phase. Updates within the same process preserve the scroll position.
- **Local persistence** — Process metadata is stored in `localStorage`; imported DXF/DWG content is stored in IndexedDB so active phases can be restored after a refresh

## Prerequisites

- Node.js **≥ 24** and pnpm **≥ 10** (monorepo workspace)
- Built dependencies before **dev** or **build**:
  - `@mlightcad/cad-simple-viewer`
  - `@mlightcad/cad-html-plugin` (produces `viewer-runtime.iife.js`, copied into the example dist)

From the repo root, a full workspace build satisfies this:

```bash
pnpm install
pnpm build
```

Or build only what this example needs:

```bash
pnpm --filter @mlightcad/cad-simple-viewer build
pnpm --filter @mlightcad/cad-html-plugin build
```

## Getting Started

### Development

From the monorepo root:

```bash
pnpm dev:simple
```

To choose the login behavior for this startup, run from the monorepo root:

```powershell
# Show the login page (also the default when omitted).
pnpm dev:simple --login=true

# Skip login and enter the workspace directly.
pnpm dev:simple --login=false
```

The startup argument does not modify env files or persist across restarts.
Only `true` and `false` are accepted. Other development server arguments are
forwarded to the existing Nx command, preserving dependency builds. Direct
workspace entry has no demo account/logout control, but keeps toolbar settings.
This switch controls the frontend demo login, not backend authorization.

Or from this package:

```bash
cd packages/cad-simple-viewer-example
pnpm dev
```

Vite prints the local URL. For host, port, backend, and proxy settings, see the root [Network Configuration](../../README.md#network-configuration).

### Production

```bash
pnpm build
pnpm preview
```

The build copies parser workers and `viewer-runtime.iife.js` into `dist/` (see `vite.config.ts`).

### Backend API

Development and deployment network settings are configured only in `.env.example`, as documented in the root [Network Configuration](../../README.md#network-configuration). Other env files, shell variables, and runtime configuration cannot override these settings. The default `http://auto:5153` follows the browser's frontend hostname when connecting directly to a backend on the same computer; the development proxy uses `127.0.0.1:5153`. The frontend listens on all IPv4 interfaces for LAN access. After switching networks, open the frontend at its new IP without editing configuration or rebuilding. Direct LAN backend access also requires backend listening/firewall/CORS configuration; use an explicit backend URL if it runs on another computer.

## Usage

### PDF report generation

Report PDFs and ZIP archives are generated by the backend. After submission,
the frontend polls `/api/v1/Skill/flow-path/result?id=...` every four seconds,
without a fixed two-minute completion deadline. `Pending` and `Running` keep
the report waiting; `Completed` must include a nonempty download `url`.
`Failed` displays an export error, and `Cancelled` displays cancellation.
For older backends that omit `status`, a nonempty `url` still indicates completion.

The PDF and Matrix export status spinner stays animated even when the operating
system or browser requests reduced motion, so ongoing generation remains visible.

Closing and reopening the report workspace does not cancel or resubmit an
in-flight export. **Cancel generation** stops the frontend wait and download;
it does not cancel the backend task. Network/API errors still stop the wait and
are displayed. Matrix export retains its existing two-minute deadline.

### Quick Phase replacement

Select a Phase in the active Sequence, click its **Copy Phase** icon, then click
another Phase in the same Sequence. Its content is replaced immediately, without
a dialog or confirmation. The source is marked **Copy source**; clicking it does
not replace itself. Press **Esc** or click its copy icon again to cancel.
Switching Process or Sequence also cancels the pending copy. No instruction
banner or cancel button is shown while choosing a target; replacement progress
and errors remain visible.

Replacement preserves the target ID, number, name, position and creation time.
Drawing association, Vessel ownership, device states, automatic flows, manual
corrections and text notes follow the source, including its latest captured edits.
The existing local/backend save path is reused. While replacing, the panel blocks
duplicate submissions and conflicting operations. Success activates the target
and exits copy mode; failure displays an error and permits retry. There is no undo
for replacement.

The separate **Create copy…** icon is hidden in the Phase list; its existing
number/name form is retained internally. Quick replacement and delete
confirmations are unchanged.

### Automatic and manual highlighting

The viewer toolbar's **Automatic highlighting** toggle belongs to the loaded
Phase's editing session, not its saved data or the user's toolbar preferences.
Modes are remembered in memory for each Project/Process/Sequence/Phase during
the current application session. Switching away and back restores the chosen
mode; reloading the application, new Phases and copies start in `auto`.
The toggle is disabled without an editable loaded Phase and while loading or
drawing a stroke.

- **On (`auto`)** preserves configured-device state selection, automatic routing,
  and device protection at brush/eraser operation entry points. It does not
  suppress or undo previously saved manual device corrections.
- **Off (`manual`)** retains existing automatic routes and device highlights but
  stops state-changing device interactions and automatic route recalculation,
  including recalculation after flow-rule edits. The brush can highlight every
  visible picked entity, including valves, devices, text and overlapping entities.
  The eraser can exclude retained automatic and device highlights. Neither tool
  changes equipment state or CAD geometry.
- Manual additions override normal highlights, and exclusions hide them.
  Invalid-device warning frames remain visible even after painting or erasing.
  Returning to automatic mode changes only future editing permissions; it does
  not change the picture, delete manual records or recalculate stored routes.
  Manual corrections remain authoritative after automatic route recalculation.
  Only undo or explicitly clearing corrections restores the corresponding base
  presentation.

Mode changes are not submitted to the backend, written to local workspace data,
or tracked as unsaved Phase changes. Obsolete persisted `highlightMode` values
are ignored on loading and omitted on subsequent saves. Manual additions and
exclusions are still saved with each Phase and survive switching or reopening,
even when the editing mode resets to automatic. The viewer and derived
`flowPaths` share a resolver that does not depend on editing mode. Consumers of
backend overlays must apply exclusions and additions before rendering
`deviceStates`; those records retain the original business states even when
their highlights have been overridden or erased. No backend mode field is
required.

### Brush debugging

Enable **Feature settings > Development > Brush debug** to show the shared
**Debug** sidebar. When valve debugging is also enabled, use the **Valve debug**
and **Brush debug** buttons to switch views.

Brush debug accumulates unique entity IDs hit by brush/eraser strokes, excluding
valves, pumps, and other protected interactive devices in automatic mode only,
using the same protection rules as painting. Each row shows its DXF entity type, layer, CAD handle, and latest operation;
missing persistent handles remain visible for diagnosis. Click a row to blink
that exact entity for 1.2 seconds without zooming, editing its highlight, changing
device states, or adding Phase data. Unavailable previews are marked explicitly.
**Clear list** clears debug history only. Opening a drawing or resetting Phase
runtime clears the list and any locator overlay. Objects missed by picking
cannot appear in this list.

Interactive-device recognition and brush protection use the device Title in
**Highlight style settings > Devices** (`devices[].name`). Only the entity's own
`ControlModules[].CadHandle` can match; its module `Name` or `YQJ_CODE` must equal
a configured Title (case-insensitive, ignoring surrounding whitespace).
Graph-inferred ownership does not make connected pipe segments devices.
Unmatched entities do not gain device interaction or brush protection merely
because they are connected to a valve or have a saved device-state record.
Right-click state selection, automatic-mode brush/eraser protection and brush
debug share this recognition rule. Rendering saved corrections never depends on
device protection. Manual mode removes operation protection without changing
device recognition or the flow graph.

### Configured-device automatic flow rules

All configured device categories (including Valve, Pump and PP) use the selected
state's `flowBehavior` and `autoHighlightFlow`, not their graph classification:

- `conducting` permits traversal and starts a route only when
  `autoHighlightFlow` is true.
- `blocking` stops traversal before the device and never starts a route.
- `neutral` permits traversal but never starts a route.
- An unselected configured device blocks. Missing, disabled or mismatched state
  references also block, retain the original state record and report a warning.
- Blocking/neutral presets cannot enable automatic flow in the style dialog;
  conflicting older configuration is also prevented from starting routes at runtime.
- A source retains its valid Utility binding. An explicit menu selection changes
  that binding; an unavailable binding falls back to the first enabled Utility
  by `order`. With no enabled Utility, the state still applies and an error is
  shown, but no automatic route is generated.

State changes recalculate all runtime automatic sources with these rules,
preserving route IDs, names and priorities. Saved rule changes update only the
currently loaded Phase after a successful style save; visual-only edits redraw
without routing. Failed style saves retain the previously active rules.
Other Phase snapshots remain unchanged. Loading a Phase
restores its stored routes without implicit recalculation. Manual additions and
exclusions are not changed by routing. Debug uses the same policies and actual
source set, distinguishing neutral, unselected and invalid-state devices.

Invalid saved device-state references never fall back to normal device or
Utility colors. The drawing keeps its CAD appearance and adds an orange frame
with a vector `!` marker above highlight layers. The context menu retains the
original state key, explains that its reference is invalid, and offers only
currently available states for explicit repair. When no states remain, it
explains how to add one instead of exposing legacy open/close actions.
Nonblocking warnings are emitted once per newly invalid reference in each
Phase, not on every recalculation or return to that Phase. Repairing the state
or restoring the original preset ID removes the marker and resets that warning
episode. Unselected devices are not marked as invalid. No warning geometry or
replacement state is persisted in Phase data.

### Manual highlight correction data

Phase JSON separates three sources and a derived final snapshot:

- `deviceStates`: equipment states, never edited by the brush/eraser.
- `autoFlowPaths`: complete automatic route records (`id`, `name`, `handleKeys`,
  required `highlightStyleRefId`, optional `ownerHandleKey` and `priority`). Route IDs and ownership
  survive round trips; restoration does not infer owners or run routing.
- `manualCorrections`: each `additions` record contains one `handleKey` and a
  required `highlightStyleRefId`; a batch stroke creates multiple records.
  `exclusions` store erased automatic-flow and device highlights. These records
  apply in every editing mode. Automatic editing skips valves and interactive
  devices; manual editing permits ordinary entity highlighting on them.
- `flowPaths`: derived final visible flow entries, composed from automatic routes
  and corrections using the same layering resolver as the viewer. Each entry has
  only `handleKey` and `highlightStyleRefId`. Device-state indicators remain in
  `deviceStates`, not in this array.

Style references point to either a Utility ID or a device-state preset ID in the
project style configuration. Configuration edits apply to existing highlights;
no inline style snapshot, `styleSource`, `styleOverride`, `utilityId`, or
`geometry` is persisted. Backend handles are decimal strings; runtime CAD
handles are hexadecimal. Local workspace schema is version 6; older local
versions are not migrated.

#### Style reference validation / 样式引用检查

`highlightStyleRefId` identifies a Utility style or a device-state style preset,
not a device object. Missing-reference checks search both ID sets, matching the
renderer: checking Utilities alone would incorrectly report valid device presets
as missing. The brush retains the selected preset ID, so later configuration
edits update existing highlights without copying an inline style snapshot.
Borrowing a device preset affects appearance only; it does not change equipment
states or trigger routing. Actual `deviceStates` are checked separately for the
referenced state style, state key, and device type.

`highlightStyleRefId` 引用 Utility 样式或设备状态样式预设，不是设备对象 ID。
缺失检查同时查找这两类 ID，与渲染解析保持一致；只查 Utility 会误报有效的设备预设。
画笔保留所选预设的原始 ID，因此修改样式配置后，已有高亮同步更新，无需保存内联样式快照。
借用设备预设仅改变外观，不修改设备状态或触发路由；真正的 `deviceStates` 仍单独检查
状态样式引用、状态键和设备类型是否匹配。

#### Removed geometry marker / 已移除的 geometry 标记

The former optional `geometry: 'bounds'` selected a rectangular marker around an
entity instead of highlighting its CAD geometry. It stored no coordinates and
did not participate in connectivity calculations. It appeared in manual addition
records, final flow records, parsing/deduplication, and the rendering branch.
Before removal, bounds-marked manual additions were already suppressed as device
markers, and normal brush strokes did not generate them. This residual support
is now removed: persisted flow highlights use the entity itself, with no geometry
field or old-data migration. Temporary valve locator frames and Three.js geometry
objects remain unchanged.

原先可选的 `geometry: 'bounds'` 表示在实体外围绘制矩形包围框，而不是沿 CAD 实体高亮。
它不保存坐标，也不参与连通计算；曾用于手工补画记录、最终流路记录、解析去重及渲染分支。
删除前，带此标记的手工记录已按设备标记抑制显示，正常画笔也不再生成它。
现在移除这部分残留支持：持久化流路高亮统一沿实体绘制，不再保存该字段或迁移旧数据。
临时阀门定位框和 Three.js 自身的几何对象不受影响。

#### Composition example / 合并示例

With no device-state override on handle `26`, excluding `43` preserves the complete
automatic route while removing `43` from the final snapshot. Each painted handle
is stored as a separate addition.

当句柄 `26` 没有设备状态覆盖时，排除 `43` 只从最终快照中移除该图元，自动流路仍保留完整成员。
批量补画中的每个句柄分别保存为一条 addition。

```json
{
  "autoFlowPaths": [{
    "id": "route-1",
    "name": "Automatic route",
    "ownerHandleKey": "26",
    "handleKeys": ["26", "43"],
    "highlightStyleRefId": "water"
  }],
  "manualCorrections": {
    "additions": [
      { "handleKey": "44", "highlightStyleRefId": "air" },
      { "handleKey": "33", "highlightStyleRefId": "air" },
      { "handleKey": "55", "highlightStyleRefId": "air" }
    ],
    "exclusions": ["43"]
  },
  "flowPaths": [
    { "handleKey": "26", "highlightStyleRefId": "water" },
    { "handleKey": "44", "highlightStyleRefId": "air" },
    { "handleKey": "33", "highlightStyleRefId": "air" },
    { "handleKey": "55", "highlightStyleRefId": "air" }
  ]
}
```

The runtime's `flowState.flowPaths` contains automatic results only and maps to
backend `autoFlowPaths`. Final `flowPaths` is generated at save/copy serialization
time, never read as a routing input. All fields are submitted in one Phase JSON
snapshot. The new backend contract requires `autoFlowPaths` and `flowPaths` arrays;
there is no fallback from a missing automatic field to the final snapshot and no
old backend-data migration. Deploy the updated backend before using this frontend.

Internal handles are hexadecimal; backend handles, including automatic route
owners and members, are decimal strings and retain large integer precision.
Explicit empty correction arrays clear corrections. Duplicate additions use the last style,
and exclusions win if imported data contains both operations for one handle.
Missing style references and unresolved handles are retained for later resolution.

The store clones corrections during phase copying/inheritance, preserves them on
flow-only updates, and clears them when a plain drawing is associated (including
the same drawing) or the drawing association is removed. Malformed correction data is reported by the overlay
parser and rejected by the repository to prevent saving a lossy snapshot.
Correction-only edits participate in the existing unsaved-highlight status.
Both local and backend drawing-association commands use the same store rules:
selecting a plain drawing clears device states, automatic flows and manual
corrections even when selecting the same drawing again. Associating a marked Phase
copies its flow/device state and corrections
independently of the source. The association dialog explains these effects before
confirmation. Loading blocks brush edits throughout association, saving and
restoration so old drawing strokes cannot overwrite the reassociated data.

The brush and eraser now edit this independent correction state:

- Painting adds or recolors a manual highlight and removes an exclusion for the
  same handle. Utility and device preset IDs are retained per object; painting
  with a device preset changes appearance only, never device states.
- Erasing removes the manual addition and excludes any currently visible
  automatic flow contribution. Erasing an empty object or device-state-only
  highlight creates no exclusion. Exclusions apply to all flows at that handle.
- Device states and routing inputs remain unchanged. Painting skips graph valves,
  objects with device states and configured interactive devices, including their
  mapped CAD handles. Saved manual marks on devices are suppressed without
  deleting their records. Selection and locator frames are unaffected. Erasing
  a flow contribution never hides the valve's state indicator.
- Automatic recomputation preserves corrections; closing a valve can therefore
  leave manually supplemented pipe segments visible. Painting an excluded object
  makes it visible again.
- Phase restoration reads manual handles directly without creating route roots.
  Unresolved handles and missing style references are retained and reported.
- The brush component only samples hits. The application owns one correction
  state and one highlight-rendering path; completed/interrupted strokes submit
  state once, including Escape, pointer cancellation and tool/phase changes.
  Loading a workspace ends the active stroke and blocks new brush activation.
- The correction bar shows addition/exclusion counts, including retained
  unresolved handles. Its correction-specific Undo/Redo buttons operate on
  complete strokes, not samples, and never undo device states or automatic flows.
  No-op strokes preserve redo; a new changed stroke discards it. History resets
  on phase/drawing restoration and is not persisted or copied between phases.
  Global CAD undo shortcuts are not intercepted.
- Clear corrections requires confirmation, removes additions and exclusions,
  and clears correction history without changing device states or automatic
  results. It cannot be undone. A confirmation from an earlier phase activation
  cannot clear another phase, including after switching away and back.
  Correction actions are disabled during drawing strokes and workspace loading.
- Brush rendering deduplicates affected objects into one animation frame and
  updates only those highlight roots. Stroke completion flushes pending rendering;
  resets and scope changes cancel old pending work.

Existing persisted flow records are not reclassified as manual corrections.
Real backend retention of `manualCorrections` and visual validation against a
customer drawing remain deployment acceptance requirements; automated tests cover
model composition, correction controls/history, rendering scheduling and mocked
backend round trips, not a full authenticated drawing workflow.

### Highlight performance

- Each full or partial highlight synchronization reads one presentation profile
  for the batch, rather than cloning the entire workspace per entity.
- Automatic routing and debug trees share one traversal kernel. Automatic routing
  collects handles without allocating debug nodes or visited-edge details.
- Disabling valve debug releases its trees without disabling configured-device
  menus, warnings, automatic routing, or brush debug. With path overlays disabled,
  trees are built only for inspected devices. Repeated refreshes reuse the
  same runtime result; state/rule, graph, workspace and Phase changes invalidate it.
  Phase restoration never triggers routing or prebuilds debug trees.
- Identical presentation values and render order do not traverse preview roots
  or update materials again. Order/visibility-only changes leave materials alone.
  Viewport resolution updates remain independent, including for newly added roots;
  disposed roots are removed from both viewport tracking and style caches.
- These caches are runtime-only. Route identity, Utility selection, priority,
  manual corrections, invalid-state blocking and saved snapshots are unchanged.

### Default Device Styles / 默认设备样式

- Built-in defaults are maintained in [defaultDeviceStyles.json](src/presentation/defaultDeviceStyles.json), using the same `presentationProfile.deviceStyles` / `utilities` format as exported files. The file can be imported directly, or replaced with a valid export; changes require rebuilding. Initialization, import, and drawing supplementation share [parseHighlightStyleDocument](src/presentation/highlightStyleDocument.ts). It validates required fields, hex colors, line widths (1-12 px), opacity (0-1), flow rules, and duplicate IDs/states before normalization. Historical backend data still uses the existing compatibility reader.
- Drawing supplementation matches Document `Areas[].ControlModules[].Name` against `deviceType`, ignoring case and surrounding whitespace, and retains the drawing's category name. To add categories, add flat `deviceStyles` entries with distinct stable IDs; the former `categoryMappings` / `templates` format is no longer used. The built-in version is maintained in [defaultDeviceStyles.ts](src/presentation/defaultDeviceStyles.ts), not in the import file.
- Template version 2 covers `Valve`: `OPEN` displays as `ON` (green `#00C853`, opacity 0.5, conducting, automatic flow highlighting enabled); `CLOSE` displays as `OFF` (gray `#B8B8B8`, opacity 0.5, blocking); `PULSE` is green `#00C853`, opacity 1, neutral. All use 3 px lines; automatic flow highlighting is off for CLOSE/PULSE. Other categories are discovered during drawing supplementation. Adding styles does not change flow-graph classification.
- New project initialization also loads two enabled Utilities from the same JSON: `Utility 1` uses cyan `#10D7DA`, 4 px, opacity 0.5; `Utility 2` uses gold `#C79C00`, 3 px, opacity 0.5. Both have stable built-in IDs. Drawing supplementation leaves Utilities unchanged, and existing projects are not automatically upgraded to these defaults.
- A project without previous style configuration loads bundled defaults when it opens, even before a phase or drawing exists. Empty device/Utility arrays without initialization metadata are treated as unconfigured, including old unmarked empty configurations. Nonempty configurations and explicitly marked empty configurations are preserved. Initialization changes neither other presentation settings, device states, nor source Document data, and does not submit to the server. Use Apply to save.
- **Add missing styles from drawing** collects distinct nonempty `Areas[].ControlModules[].Name` values across all areas. The preview counts new categories/states, not individual drawing objects. A missing category without a template receives generic `OPEN` / `CLOSE` states displayed as `ON` / `OFF`, green `#00C853` / gray `#B8B8B8`, 3 px, opacity 1, neutral flow behavior, and automatic flow highlighting off. Existing categories without templates are left unchanged. Confirmation appends only missing categories or template states; existing IDs, colors, utilities, and states are preserved. Cancel leaves the project unchanged. Repeating creates no duplicates. `Valve1` remains distinct from `Valve`.
- `presentationProfile.defaultStyleSeed` records `pending`, `generated`, or `configured`, with the template version when generated. Initialization assigns `generated`; confirmed imports and explicit user edits assign `configured`. Saving an explicit empty configuration prevents automatic regeneration only when the backend retains this metadata in saveStyle/configure round trips. Without metadata, an old intentionally cleared configuration cannot be distinguished from a new empty project and will load defaults. Template upgrades never overwrite marked or nonempty project settings.

- 内置默认配置位于 [defaultDeviceStyles.json](src/presentation/defaultDeviceStyles.json)，采用与导出文件相同的 `presentationProfile.deviceStyles` / `utilities` 格式，可直接导入，也可用有效导出文件替换；修改后需要重新构建。初始化、导入和按图纸补齐共用 [parseHighlightStyleDocument](src/presentation/highlightStyleDocument.ts)，在归一化前校验必填字段、十六进制颜色、线宽（1-12 px）、透明度（0-1）、流路规则及重复 ID/状态。后台历史数据仍使用原有兼容读取逻辑。
- 按图纸补齐通过 `deviceType` 匹配 Document 的 `Areas[].ControlModules[].Name`，忽略大小写和首尾空格，生成类别名保留图纸原名。扩展类别时在 `deviceStyles` 中新增扁平记录并设置唯一稳定 ID，不再使用原 `categoryMappings` / `templates` 格式。内置版本号在 [defaultDeviceStyles.ts](src/presentation/defaultDeviceStyles.ts) 中维护，不属于导入文件格式。
- 模板版本 2 包含 `Valve` 三状态：`OPEN` 显示为 `ON`（绿色 `#00C853`、透明度 0.5、导通、开启自动流路高亮）；`CLOSE` 显示为 `OFF`（灰色 `#B8B8B8`、透明度 0.5、阻断）；`PULSE` 为绿色 `#00C853`、透明度 1、中性。线宽均为 3 px，CLOSE/PULSE 关闭自动流路高亮。其他类别在按图纸补齐时读取，增加样式不会改变流路图的设备分类。
- 新项目初始化时还从同一份 JSON 加载两套已启用的 Utility：`Utility 1` 为青色 `#10D7DA`、4 px、透明度 0.5；`Utility 2` 为金黄色 `#C79C00`、3 px、透明度 0.5。两者使用稳定的内置 ID。“根据图纸补齐”不修改 Utility，已有项目不会自动升级为这些默认值。
- 从未配置样式的项目在打开时即加载内置默认配置，不必先创建阶段或加载图纸。无初始化标记且设备/Utility 均为空时视为未配置，包含无标记的旧空配置；非空配置和带明确标记的空配置保持不变。初始化不修改其他显示设置、设备当前状态或源 Document，也不自动提交后台，需要点击“应用”保存。
- “根据图纸补齐”读取所有 Area 下的 `ControlModules[].Name`，过滤空名称并去重。预览统计新增类别和状态，而不是图纸中的设备实例数。缺失且无模板的类别新增通用 `OPEN` / `CLOSE` 状态，显示为 `ON` / `OFF`，绿色 `#00C853` / 灰色 `#B8B8B8`，线宽 3 px、透明度 1、中性流路行为、关闭自动流路高亮。已存在且无模板的类别不补写通用状态。确认后只追加缺失类别或模板状态，保留已有 ID、颜色、Utility 和状态；取消不影响项目，重复操作不产生重复项。`Valve1` 与 `Valve` 保持为不同类别。
- `presentationProfile.defaultStyleSeed` 保存待初始化、已生成或用户配置状态，以及生成时的模板版本。初始化标记为 `generated`，确认导入和显式编辑标记为 `configured`。后台须在 saveStyle/configure 往返中保留此字段，才能保证主动清空后不自动恢复；无标记的旧主动清空配置无法与新项目区分，会加载默认值。模板升级不覆盖带标记或非空的项目配置。

### Drawing Workflow

1. Start the dev server and open the URL shown in the terminal.
2. Open the **工艺与阶段** dock tab, create a process such as `CIP`, then create its first phase from a local drawing, drawing URL, or blank drawing.
3. Later phases can use the previous marked drawing, any historical phase, or a new drawing. Cloned highlight and device state is independent from its source phase.
4. A phase drawing can be renamed from its overview. This changes only the business display name; it does not rename the original file or change the default export file name.
5. **Predefined files** — Click a name in the left sidebar to load a sample from the CDN outside the current phase workflow.
6. **Your own file** — Click **Open File** (empty state) or **Open** (toolbar) to open an ad-hoc `.dxf` or `.dwg` without replacing phase metadata.
7. After a drawing loads, use the toolbar:
   - **Zoom Fit** / **Zoom to Window** — `ZOOM` commands
   - **Switch BG** — Toggle drawing background
   - **Set Pickbox** — Prompt to set `PICKBOX` system variable
   - **LineWeight: On/Off** — Toggle `lwdisplay` on the current database
   - **Export HTML** / **Export PDF** — Run `chtml` / `cpdf` from the toolbar (`chtml` uses command-line prompts here; `-chtml` is equivalent). Plugins must be registered; see `src/main.ts`.

Toast messages at the top report success or errors. The window title updates when a document is activated.

The PHASE dropdown lists every phase in the active sequence with its full name.
Its width adapts to the label (at least 160px), with horizontal scrolling in
compact layouts when needed. Browsers without CSS `field-sizing` support use
the native select's intrinsic option width.

In the Phase list, green numbers indicate an assigned drawing, black numbers
indicate no drawing, and amber numbers warn that the assigned drawing asset is
missing. Hover tips and accessible labels describe the status without a separate
text column.

The process/phase sidebar keeps its current scroll position when selecting a
Phase or refreshing the panel, including after asynchronous drawing loading.
If the content becomes shorter, the browser clamps scrolling to the available
range rather than resetting it to the top.
Selecting a Phase from the top PHASE dropdown also expands its Sequence in the
sidebar and scrolls only that sidebar enough to show the selected row. An already
visible row does not move, and later drawing-load redraws retain this position.
If a Vessel filter hides the selected Phase, it switches to All Vessels and stops
Vessel locating so the selected Phase can be shown. Clicking rows directly and
ordinary panel refreshes still preserve the user's scroll position.
While dragging a Phase, hold the pointer within 48 pixels of the scrolling
content's top or bottom edge to scroll continuously, even without moving the
pointer. Scrolling accelerates toward the edge (up to 600 pixels/second).
Drop onto the desired Phase once it is visible to reorder within the Sequence.
Moving away from the edge, dropping, or cancelling the drag stops auto-scrolling.
The process heading, selector, and add/delete controls stay fixed at the top of
the sidebar while the content below scrolls independently. The inline process
creation form also stays in this fixed header when expanded.

## What this example demonstrates

Integration patterns useful when building your own host app (not a full CAD UI like `@mlightcad/cad-viewer`):

| Topic | Implementation |
|-------|----------------|
| Document manager | `AcApDocManager.createInstance({ container, baseUrl, webworkerFileUrls, commandAliases, … })` |
| Local open | `openDocument(name, ArrayBuffer, options)` with `AcApOpenDatabaseOptions` |
| Remote open | `openUrl(url, options)` for CDN sample files |
| Commands | `sendStringToExecute('zoom\\nall')`, `switchbg`, plugin commands `chtml` / `-chtml` / `cpdf` |
| System variables | `AcDbSysVarManager` + `sendStringToExecute` (e.g. `PICKBOX`) |
| Plugins | Lazy registration via `@mlightcad/*/register` in `src/register.ts` (only needed plugins) |
| Command aliases | Demo overrides (`LINE` → `LX`, etc.) via `commandAliases` |
| Workers & assets | `webworkerFileUrls`, `htmlViewerRuntimeUrl`, static copy in Vite |

The document manager initializes at page load so the process/phase dock is available in an empty workspace. CAD documents and export plugins continue to load on demand.

### Local phase data

- `localStorage` key `cad-simple-viewer-example-phase-workspace` contains versioned process, phase, drawing-reference, highlight-handle, and device-state metadata.
- IndexedDB database `cad-simple-viewer-example`, object store `drawing-assets`, contains imported local drawing content.
- Remote drawings persist their URL; blank drawings persist a reconstructable drawing reference.
- Clearing site data removes both the workspace metadata and stored local drawings.
- If a stored drawing is unavailable, its process and phase metadata remains visible so the drawing can be re-associated later.
